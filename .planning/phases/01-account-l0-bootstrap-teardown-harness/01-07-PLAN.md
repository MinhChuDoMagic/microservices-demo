<objective>
Federate GitHub Actions to AWS with trust scoped to this repository and to a specific ref, and
create the two CI roles the rest of the project assumes exist.

Purpose: this is the phase's highest-severity security surface and its most likely silent breakage,
for two unrelated reasons. A trust policy that omits the subject condition, or widens it with a
wildcard, lets workflows in repositories this operator does not control assume an
administrator-equivalent role — and on a personal account, creating a new repository under your own
name is a two-click operation. Separately, GitHub changed the subject claim format for repositories
created after mid-2026; a policy written against the older literal form never matches such a
repository, and the failure surfaces only at the first CI run with an error that names nothing
useful. The second is why this plan opens with a decision checkpoint rather than an apply.

Output: one OIDC provider, two roles with disjoint trust, and static assertions that the policies
are scoped the way they are claimed to be.

Ordering: this plan runs after 01-06 rather than beside it. Both add resources to
`layers/00-bootstrap` and both assert a clean `plan -detailed-exitcode` afterwards, so running them
in one wave means either two concurrent applies contending on the same native state lock, or a
sequential pair in which each plan's clean-plan assertion is falsified by the other's not-yet-applied
configuration. Their `files_modified` sets do not intersect, so the wave overlap guard cannot see
this — the dependency edge is the only thing that expresses it.
</objective>

    role is written. GitHub repositories created on or after 15 July 2026 emit a subject claim that

    is a property of this repository today, not a property of the project.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions workflow -> AWS STS | The trust policy is the entire access-control surface; there is no network boundary, no secret, and no second factor behind it. |
| any GitHub repository on the internet -> this role | Without a subject condition, any workflow anywhere can mint a token with the shared audience value and assume the role. |
| CI role -> the AWS account | The apply role is administrator-equivalent by design in this phase. |
| CI role -> long-lived credentials | A role able to create IAM users or access keys can manufacture exactly the credential class the project forbids. |
