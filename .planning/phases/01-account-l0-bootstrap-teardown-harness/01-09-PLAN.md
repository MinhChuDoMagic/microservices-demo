<objective>
Prove the hard gate: `scripts/verify-teardown.sh` exists and is demonstrably capable of failing.
Then prove the credential half of success criterion 5, and record the one convention this phase
establishes with no instance to apply it to.

Purpose: a verifier nobody has seen fail is indistinguishable from a verifier that always passes.
The roadmap's hard gate is not "the script exists" — it is "the script is demonstrably capable of
failing before Phase 2 provisions anything", and the only honest form of that is a committed,
repeatable test rather than a one-time manual ceremony. The third arm matters most: the
error-exit path is exercised by nothing else in the project, so it is the arm most likely to rot
into a silent pass, and a silently broken verifier reporting a clean account is the worst outcome
this phase has.

Output: a repeatable three-arm test costing a fraction of a cent per run, a scripted proof that no
long-lived credential exists on either side, and a retention convention with a guard instead of a
placeholder.

This plan's dependency on 01-06 is retained deliberately. Arm 2 of the hard-gate test creates a real
billable EBS volume in the account, so the cost guardrails — the SNS topic, both budgets and the
anomaly monitor — are applied and their alert path confirmed before anything here deliberately
spends money. The cost allocation tag activation that used to sit behind that dependency has been
moved out of 01-06 into the terminal plan 01-10, so the hard gate is no longer sequenced behind the
billing console's multi-hour key-propagation window; what remains in 01-06 is a click-through email
confirmation with no external latency of its own.
</objective>

  <action>
    Write `scripts/test-verify-teardown.sh` with three arms, in this order.

    **Arm 1 — clean baseline.** Run the sweep and assert the clean exit code. If this fails, stop
    immediately and say so: the account was already dirty and the rest of the test would be
    measuring the wrong thing.

    **Arm 2 — a real orphan.** Create one untagged 1 GiB general-purpose EBS volume in the home
    region. Install the cleanup trap that deletes it **before** the create returns into any other
    logic, so an interrupt between create and assert still cleans up. Wait for the volume to reach
    the detached state the sweep filters on, then run the sweep and assert the orphans exit code and
    assert that the volume's identifier appears in `.teardown-report.json` under the volumes class.
    Asserting the identifier, not only the exit code, is what proves the sweep found *this* volume
    rather than something else. Delete the volume, wait for it to disappear, run the sweep again and
    assert the clean exit code. The volume is deliberately untagged: a tag-only sweep would score it
    clean, and this arm is what proves the blind-spot layer is doing real work.

    **Arm 3 — a broken verifier.** Re-run the sweep in a subshell with deliberately invalid
    credentials in the environment. Assert the error exit code, and separately assert that the output
    does **not** contain the clean verdict string. Both assertions are needed: an exit code alone
    would still pass if the script printed a clean verdict and then exited non-zero for an unrelated
    reason. This arm exercises the path that distinguishes "the account is dirty" from "I could not
    answer", and nothing else in the project ever runs it.

    Use a cleanup trap covering normal exit, error exit and signals, and make the trap idempotent so
    a second invocation cannot fail. Print a one-line per-arm result and a final summary. Keep the
    whole run under two minutes; the volume create and delete round-trip dominates.

    Wire `make test-verify-teardown` to run it with `doctor` as a prerequisite, mapping each arm's
    failure to a distinct message. Record in a Makefile comment that this target costs a fraction of
    a cent per run and is safe to run repeatedly.
  </action>

| verifier exit code -> the Phase 2 gate | Phase 2 refuses to proceed on this code. A verifier that cannot fail makes the gate decorative. |
| long-lived credential -> the account | The single most common cloud credential leak vector, and the one this project's constraints forbid outright. |
